Phase 2: Host Storage Optimization & LVM Expansion

During initial deployment, the Ubuntu root partition (/) was 97% full (only 415 MB free), which would cause Splunk installation to abort. Ubuntu Server's LVM installer defaults to provisioning only 50% of the virtual drive.

2.1 Unlocking Hidden LVM Disk Space

# Check physical drive size and LVM Volume Group status
sudo lsblk
sudo vgs

# Extend the logical volume to claim 100% of unallocated disk space (+11.5 GB)
sudo lvextend -l +100%FREE /dev/ubuntu-vg/ubuntu-lv

# Expand the filesystem live without rebooting
sudo resize2fs /dev/ubuntu-vg/ubuntu-lv

# Verify storage (Space expands from 775 MB to 12+ GB available)
df -h /

Phase 3: Splunk SIEM Deployment & Service Initialization

3.1 Download and Install Splunk Enterprise

# Download Splunk 9.2.2 .deb package directly via wget
wget -O splunk.deb "https://download.splunk.com/products/splunk/releases/9.2.2/linux/splunk-9.2.2-d76edf6f0a15-linux-2.6-amd64.deb"

# Install package onto Ubuntu (installs to /opt/splunk)
sudo dpkg -i splunk.deb

3.2 Start Splunk & Set Admin Credentials

# Start Splunk daemon and accept software license
sudo /opt/splunk/bin/splunk start --accept-license

# Configure Administrator Credentials when prompted:
# Username: admin
# Password: [YourStrongPassword]

# Configure Splunk to launch automatically upon system boot
sudo /opt/splunk/bin/splunk enable boot-start

3.3 Firewall Configuration & Web Access

# Open Splunk Web GUI port (8000/TCP) in Ubuntu firewall
sudo ufw allow 8000/tcp

# From Kali Linux (10.0.0.3) browser, navigate to:
# http://10.0.0.5:8000

Phase 4: Telemetry Pipeline & Log Ingestion Configuration

To detect multi-vector attacks, Splunk was configured to ingest both operating system authentication telemetry and application firewall logs.

4.1 Granting File Permissions on Target Host

By default, Ubuntu restricts `/var/log/apache2/` to root/adm. Ensure Splunk has read access:

# Set read permissions for log monitoring
sudo chmod 644 /var/log/auth.log
sudo chmod 644 /var/log/apache2/*.log

4.2 Ingesting Telemetry Sources (Splunk Web UI or CLI)

Option A: Web UI Configuration

  1. Navigate to Settings > Data Inputs > Files & Directories > click + Add New.
  2. Input 1 (SSH Auth Logs):
    • File Path: /var/log/auth.log
    • Source Type: Operating System > linux_secure
    • Index: main (Default)
  3. Input 2 (Web/WAF Logs):
    • File Path: /var/log/apache2/error.log
    • Source Type: apache_error
    • Index: main (Default)

Option B: CLI Direct Ingestion Command (Faster)

sudo /opt/splunk/bin/splunk add monitor /var/log/auth.log -sourcetype linux_secure -auth admin:[Password]
sudo /opt/splunk/bin/splunk add monitor /var/log/apache2/error.log -sourcetype apache_error -auth admin:[Password]

Phase 5: Attack Simulation Execution (THC-Hydra)

From the Kali Linux attacker station (10.0.0.3), simulate an automated credential-stuffing attack targeting OpenSSH on Ubuntu (10.0.0.5).

5.1 Generating Target Credential Wordlists

# Generate user dictionary
cat << 'EOF' > /tmp/users.txt
root
admin
ubuntu
guest
test
EOF

# Generate password dictionary
cat << 'EOF' > /tmp/passwords.txt
123456
password
admin123
letmein
qwerty
toor
dragon
welcome
ninja
master
EOF

5.2 Executing Automated SSH Brute Force

# Execute multi-threaded SSH credential guessing attack
hydra -l root -P /tmp/passwords.txt -t 4 -V ssh://10.0.0.5

# (Optional Multi-User Enumeration)
hydra -L /tmp/users.txt -P /tmp/passwords.txt -t 4 ssh://10.0.0.5
Simulation Finding: Hydra initiated 4 concurrent tasks, generating 10 rapid authentication attempts against user root. All attempts returned authentication failure (0 valid passwords found), successfully flooding /var/log/auth.log with forensic telemetry.

Phase 6: SIEM Threat Hunting, SPL Queries & Forensic Analysis

In Splunk Web (Apps > Search & Reporting), execute the following Search Processing Language (SPL) queries to investigate the attack:

6.1 Core Investigation Queries

  • Detect All Failed Logins: 
    index=* sourcetype=linux_secure "Failed password"
  • Attacker Source IP Attribution & Attempt Counts: 
    index=* sourcetype=linux_secure "Failed password" 
| rex "from (?<attacker_ip>\d+\.\d+\.\d+\.\d+)" 
| stats count as "Failed Attempts" by attacker_ip 
| sort - "Failed Attempts"
  • Failure Rate Spike Analysis Over Time: 
    index=* sourcetype=linux_secure "Failed password" 
| timechart span=1m count
  • Targeted Usernames Breakdown: 
    index=* sourcetype=linux_secure "Failed password" 
| rex "Failed password for (invalid user )?(?<target_user>\S+)" 
| stats count by target_user
  • Correlated Web Application Threat Telemetry: 
    index=* source=*apache* "Access denied with code 403"

Phase 8: System Hardening & Incident Remediation

To close the vulnerability exposed during the simulation, execute the following host hardening controls on the Ubuntu server:

8.1 Deploy Fail2ban (Automated Intrusion Prevention)

# Install Fail2ban package
sudo apt-get install -y fail2ban

# Create local configuration override
sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local

# Configure SSH protection jail in /etc/fail2ban/jail.local:
# [sshd]
# enabled = true
# port = 22
# filter = sshd
# maxretry = 5
# bantime = 3600
# findtime = 600

# Restart and verify Fail2ban status
sudo systemctl restart fail2ban
sudo fail2ban-client status sshd

8.2 Hardening SSH Daemon Configuration (/etc/ssh/sshd_config)

# Disable direct root administrative login
sudo sed -i 's/#PermitRootLogin prohibit-password/PermitRootLogin no/' /etc/ssh/sshd_config
sudo sed -i 's/PermitRootLogin yes/PermitRootLogin no/' /etc/ssh/sshd_config

# Disable password authentication (Enforce SSH Public-Key Only)
sudo sed -i 's/#PasswordAuthentication yes/PasswordAuthentication no/' /etc/ssh/sshd_config
sudo sed -i 's/PasswordAuthentication yes/PasswordAuthentication no/' /etc/ssh/sshd_config

# Restart SSH service
sudo systemctl restart ssh
